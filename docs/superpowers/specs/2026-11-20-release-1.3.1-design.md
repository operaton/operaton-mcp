# Release 1.3.1 — deploy and request-body fixes

## Intent

Ship patch release 1.3.1 of `@operaton/mcp` fixing two user-reported bugs that make
core tools unusable (#113 deploy, #114 request bodies). Release from a maintenance line
`release/1.3.x` (branched from `v1.3.0`), so the release workflow must support patch
releases from `release/<major>.<minor>.x`.

## Goals

- #113: `deployment_create`, `processDefinition_deploy`, `decision_deploy` deploy successfully.
- #114: every generated tool with a JSON request body advertises the body's fields in its
  input schema, so clients send typed values (e.g. `variables` as an object, not a string).
- Release workflow can do real releases from `release/X.Y.x` and bumps to next patch SNAPSHOT there.
- Dependencies at latest.

## Non-goals

- New tools or features.

## Anti-goals

- Coercing JSON strings with `JSON.parse` in handlers (hides the bug, clients still lack a schema).
- Emitting `$ref`/`$defs` in tool schemas (many MCP clients handle them poorly).

## Approaches (#114)

- **A. Inline body schemas per tool — chosen.** Generator converts each operation's
  `requestBody` JSON Schema to Zod source, inlining `$ref`s; merges body fields with path/query params.
- B. Shared component module with `z.lazy` — rejected: `tools/list` would expose `$ref`/`$defs`.
- C. Hand-model common fields only — rejected: leaves most of 143 body operations untyped.

## Design

### #113 Multipart deploy

- `OperatonClient.postMultipart(path, { fields, files })`; `files: Array<{ name, filename, content, contentType? }>`.
  Each file appended as `new Blob([content], { type })` with explicit filename.
- `decision_deploy` gets its own schema: `dmn-content`, `dmn-filename` (default `decision.dmn`).
  `deployment_create` / `processDefinition_deploy` keep BPMN params.

### #114 Generator

- `parseSpec` keeps the `application/json` request body schema (not just a boolean).
- New converter JSON Schema → Zod source: `object` (with `required` → non-optional), `array`,
  `string` (enum → `z.enum`), `integer`/`number`, `boolean`, `nullable`, `additionalProperties`
  → `z.record`, `$ref` inlined. Cycle or depth > 4 → `z.unknown()`. Spec `description` → `.describe()`.
- Body properties merged into the top-level input object. Path/query param wins on name
  collision (e.g. `id` in `updateTask`); body copy skipped.
- Non-object bodies (arrays, untyped) exposed as single `body` field; handler sends `input.body`.
- `.passthrough()` kept for object bodies.
- Handler: body built from the declared body property names (not "everything except path params"),
  plus passthrough extras.

### Tests

- Unit: every exposed generated tool's JSON schema declares every top-level property of its request body.
- Unit: `decision_evaluate` schema types `variables` as object; multipart client sends file parts with filename.
- Integration against a real Operaton Docker container: deploy BPMN, deploy DMN, evaluate decision
  with `variables` object.

### Release workflow

- Real release allowed on `main` or `release/[0-9]+.[0-9]+.x`.
- Final release post-bump: `main` → next minor SNAPSHOT; `release/*` → next patch SNAPSHOT.
- `release/1.3.x` version set to `1.3.1-SNAPSHOT`.

## Flow

1. `release/1.3.x` from `v1.3.0`; version change to `1.3.1-SNAPSHOT` as its own commit
   (`chore: set version 1.3.1-SNAPSHOT`), push.
2. Feature branch `fix/1.3.1-deploy-and-request-bodies` off `release/1.3.x`.
3. Fix, test, bump deps — one commit per concern (#113, #114, workflow, deps, spec doc), no version changes.
4. **PR 1** feature → `release/1.3.x`, wait for CI, merge (merge commit keeps fix commits cherry-pickable).
5. Trigger `Release` workflow on `release/1.3.x` with `release_type=final`, `dry_run=true`.
6. **PR 2 forward-port:** branch `fix/forward-port-1.3.1` off `main`, cherry-pick the fix commits
   (not the version commit), resolve conflicts, PR → `main`.
7. **PR 3 backmerge:** `release/1.3.x` → `main` (merge, keeping `main`'s `1.4.0-SNAPSHOT` version),
   so `main` records the release line's history. Opened after PR 2; left open for review.
